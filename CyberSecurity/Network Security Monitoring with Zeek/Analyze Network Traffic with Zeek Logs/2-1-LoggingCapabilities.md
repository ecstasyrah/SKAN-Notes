## Tool Capabilities and Logging Formats
Zeek is a passive, open-source network security monitoring tool that analyzes traffic across the network out of the box (including HTTP sessions, DNS conversations, and web applications).

### 1. Detection and Integration
*   **Beyond Traditional IDS:** 
    - Functions as an IDS or network traffic analyzer using mechanisms beyond traditional signature-based approaches.
    - Capable of detecting threats like brute force attacks, SQL injection, and malware downloads.
*   **Scripting Integrations:** 
    - Features the ability to trigger external processes directly from within its scripting language.

### 2. Log Exporting
*   **ASCII Logs:** 
    - Standard default output showing signature hits, exportable to SIEM platforms like Splunk.
*   **JSON & Other Formats:** 
    - Supports JSON and additional formats for easier ingestion, reading, and parsing by sophisticated applications and SIEMs.

---

## Common Zeek Log Types
Zeek generates various logs ranging from connection tracking and protocol details to debugging and anomalies.

### 1. Network and Protocol Logs
*   **Connection Log:** conn.log
    - Tracks and documents all network connections seen by Zeek.
*   **Protocol-Specific Logs:** http.log / ssh.log
    - Captures detailed protocol information (such as HTTP headers or SSH data).

### 2. System and Anomaly Logs
*   **Debug and System Logs:** loaded_scripts.log
    - Identifies loaded configurations and reports system errors.
*   **Custom Logs:** 
    - User-defined logs created for specific monitoring needs.
*   **Weird Log:** weird.log
    - Documents activity that veers outside the typical behavior of a protocol or service.

## Log Structure and Organization
Understanding how Zeek stores, rotates, and organizes its log files.

### 1. The Connection Log (conn.log)
*   **Connection Events:** 
    - Tracks every connection Zeek observes or processes, where each line represents a distinct connection event.
    - Serves as base data that other Zeek analyzers can use to extract deeper context.
*   **Header Fields:** 
    - Contains built-in headers such as originating hosts, originating ports, responding hosts/ports, protocols, durations, and byte counts.

### 2. Directory Layout and Log Rotation
*   **Current Directory (`current/`):** 
    - Holds active log files generated by default network analysis (such as `conn.log`, `dns.log`, `ntp.log`, `software.log`, and `ssh.log`).
    - The primary location tapped when forwarding data to a SIEM.
*   **Archived Directories:** 
    - Zeek automatically rotates and archives logs once a day into date-stamped directories.
    - Archived files are labeled by log type and generation hour, and are saved in compressed `.gz` format.

## Log Parsing and Analysis
Techniques for extracting specific data points from default ASCII log formats.

### 1. Using zeek-cut
*   **Purpose:** 
    - Extracts specific fields based on log header names, avoiding clutter caused by long, jumbled lines in terminal displays.
*   **Usage Example:** 
    - Uses syntax like `zeek-cut <field_name> < <log_file>` (for example, extracting host IP addresses using `zeek-cut host < software.log`).

```bash
#get inside the directory of zeek
cd /opt/zeek
ls logs/ #shows the log rotation happening; other dates you can see are archived
ls logs/current 
#ls logs/<date> to show logs made that specific date
cat conn.logs
# open a log by cat <log file; check ls of logs>
cat software.logs 
zeek-cut #chooses which variables you need for logs
# Syntax : zeek-cut <field> < <log>
zeek-cut host < software.log 


```

## Framework Overview
The logging framework provides the structure for how Zeek records, formats, and outputs observed network events.

### 1. Operational Flow
*   **Event-Driven Logging:** 
    - Operates throughout Zeek's processing lifecycle, primarily triggering after Zeek detects and handles an event.
*   **Core Purpose:** 
    - Validates operational status, stores connection details, and provides visibility into network traffic data.

---

## Core Components
The framework relies on three main subcomponents to process and export data.

### 1. Streams, Filters, and Writers
*   **Streams:** 
    - Define the structure of a log, including the specific set of field names and data types.
*   **Filters:** 
    - Attached to streams to control which records and fields are recorded to disk (by default, everything in a stream is logged).
*   **Writers:** 
    - Attached to filters to define the output format (the ASCII writer is enabled by default, with alternatives like JSON and SQLite available).

---

## Customization and Scripting
Using Zeek scripts to customize how data is handled and displayed.

### 1. Log Manipulation Capabilities
*   **Field Modifications:** 
    - Add, remove, or rename fields within a log (such as renaming `proto` to `protocol_modified`).
*   **Traffic Filtering:** 
    - Exclude specific types of network activity from being logged (such as filtering out SSH connections).
*   **Operational Control:** 
    - Customize output directories, rename log files, configure log rotation schedules, and delay log writing when needed.

### 2. Viewing Data with zeek-cut
*   **Parsing ASCII Logs:** 
    - Command-line utility designed to extract specific fields from default ASCII logs, making data easy to read in the terminal.

## Log Parsing Overview
Introduction to the `zeek-cut` tool and its primary purpose in log analysis.

### 1. The zeek-cut Tool
*   **Purpose:** 
    - A utility provided by Zeek to parse logs and clean up the command-line interface view.
*   **How It Works:** 
    - Interacts with Zeek's native TSV (ASCII) formatted logs.
    - Parses the header in each file, allowing users to reference and extract specific columns of data by name.

---

## Practical Application and Analysis
Using `zeek-cut` commands in combination with standard Linux utilities to extract and analyze network data.

### 1. Extracting Specific Data
*   **Selecting Fields:** 
    - Pulls specific columns, such as originating and responding IP addresses (`id.orig_h` and `id.resp_h`) from `conn.log`, or unique fields like `query` from `dns.log`.
*   **Including Headers:** 
    - Using the `-c` flag ensures the original headers are included in the command output for better context and readability.

### 2. Filtering and Sorting
*   **Command Combinations:** 
    - Can easily be piped with other Linux commands like `head`, `sort`, `uniq`, and `grep` to filter, count, and organize data.
*   **Analysis Use Cases:** 
    - Useful for identifying top talkers, finding the highest frequency of specific DNS requests, or searching for exact query strings (such as `grep ubuntu`).
    - Helps extract actionable information to create incident tickets or establish pivot points for further investigation.

```bash
zeek-cut id.orig_h id.resp_h < conn.log # no header
zeek-cut id.orig_h id.resp_h < conn.log | head # with header 
+ sort | uniq -c #unique count

zeek-cut id.orig_h <conn.log | sort | uniq -c | sort -nr | head

#Cleaner way to look at logs (weird.log)

zeek-cut -C id.orig_h id.orig_p id.resp_h id.resp_p notice < weird.log | head

```

## Running Zeek for Analysis
Zeek can be run continuously in the background or as a single instance to analyze small amounts of data, such as a PCAP file.

### 1. Command-Line Options
*   **The `-r` Flag:** 
    - Used to specify a trace file (like a PCAP) for Zeek to read and analyze.
*   **The `-C` Flag:** 
    - Instructs Zeek to ignore TCP checksum errors.
    - Useful for filtering out noise caused by checksum offloading without affecting the analysis of the network streams.

---

## Log Interpretation with zeek-cut
Using the `zeek-cut` tool to extract specific fields and interpret network activity across various logs.

### 1. The notice.log
*   **Purpose:** 
    - Records alerts and notifications as part of the notice framework.
    - Can be used to trigger responses like scripts with webhooks and other integration mechanisms.
*   **Analysis:** 
    - Filtering by timestamp, hosts, ports, and messages can reveal system issues, such as capture losses (where port and IP fields may be blank).

### 2. The ssh.log
*   **Purpose:** 
    - Tracks SSH connections observed on the network.
*   **Analysis:** 
    - Extracting fields like the timestamp, client, and the source/destination IPs and ports helps identify the specific endpoints involved in an SSH session.

### 3. The weird.log
*   **Purpose:** 
    - Documents unusual activity or behavior that veers outside typical protocol standards.
*   **Analysis:** 
    - Includes a `name` field that identifies the specific "weird" event (e.g., data transferred before a connection was established, or reusing active connections via port 443).
    - Many of these are built-in detections that can be tuned out on a newly installed system to reduce noise.

### 4. The files.log
*   **Purpose:** 
    - Records details about files detected being transferred across the network.
*   **Analysis:** 
    - Useful fields to extract include the source/destination IPs and ports, file names, local origin, and file hashes (like `sha1` and `sha256`).
